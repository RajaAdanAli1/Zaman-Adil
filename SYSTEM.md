# zamanadil.com — What This Site Is and How It Works

## What this website is

**zamanadil.com** is the faculty website of **Dr. Adil Zaman**, a political scientist at the University of Gujrat. It is a public academic presence for his profile, research areas, publications, writing, and professional enquiries — plus a private **archive desk** for managing that content.

Visitors use the site to:

- Learn who Dr. Zaman is and what he researches (elections, political behaviour, Pakistan and South Asia)
- Browse scholarly **publications** with links to journals, DOIs, or full text
- Read **research reviews** and **opinion / blog** pieces
- See available **research services** and send a **contact** enquiry
- Search across pages, publications, and articles

The site owner uses the admin desk to edit publications and articles, read contact messages, and see basic page-view stats.

---

## High-level system

The project is a **MERN** application:

| Layer | Technology | Role |
|--------|------------|------|
| Client | React + Vite | Public pages and admin UI in the browser |
| API | Express (Node.js) | JSON API, auth, SEO files, and production static hosting |
| Database | MongoDB (via Mongoose) | Publications, articles, messages, users, page views |

```
Browser (React)
    │  /api/*  (dev: Vite proxies to port 5000)
    ▼
Express server (:5000)
    │
    ▼
MongoDB  (MONGO_URI, local Mongo, or in-memory for local dev)
```

**Local development**

- Site UI: `http://localhost:5173`
- API: `http://localhost:5000`
- Vite proxies `/api`, `/robots.txt`, and `/sitemap.xml` to the API

**Production-style run**

- The client is built into `client/dist`
- Express serves that build and injects SEO metadata per route
- Same process also serves the API

## How data flows

### 1. Reading the site

1. React loads a page and calls `api()` in `client/src/api.js` (cookie credentials included).
2. Express public routes under `/api` query MongoDB.
3. Responses are shaped by `present.js` (clean fields for the UI) and returned as JSON.
4. The page renders lists, detail views, or search results.

Important public endpoints:

- `GET /api/home` — featured publications + latest reviews/opinions
- `GET /api/publications` — list + available years/types
- `GET /api/publications/:slug` — one publication
- `GET /api/publications/bibtex` — downloadable BibTeX export
- `GET /api/articles?kind=review|opinion` — article lists
- `GET /api/articles/:slug` — article + related pieces
- `GET /api/search?q=` — pages, publications, and articles
- `POST /api/contact` — store an enquiry
- `POST /api/track` — increment daily page-view counters

### 2. Contact form

1. Visitor submits name, email, enquiry type, subject, message, and consent.
2. Server rejects empty required fields, invalid email, or unknown enquiry types.
3. A honeypot field (`website`) silently accepts bots without storing mail.
4. Rate limit: hashed IP, max 5 messages per 10 minutes.
5. Message is stored in MongoDB; the desk can mark it read or delete it.

### 3. Page tracking

On navigation, the client can `POST /api/track` with the path. Counts are stored per path and calendar day (`Pageview` model) and summarised on the admin stats panel.

### 4. SEO and sharing

- `GET /robots.txt` and `GET /sitemap.xml` are generated by the server.
- In production, when `client/dist` exists, Express serves the SPA and **rewrites HTML meta** for each path via `seo.js` so crawlers and link previews see the right title and description.

## Database models

| Model | What it stores |
|--------|----------------|
| **Publication** | Slug, title, authors, year, venue, type, volume/issue/pages, DOI, URL, PDF, summary, featured flag |
| **Article** | Slug, kind (`review` or `opinion`), title, date, category, body paragraphs/sections, publish flag |
| **Message** | Contact form submissions (name, email, enquiry, subject, message, read state) |
| **User** | Admin username, password hash, `mustChangePassword` flag |
| **Pageview** | Path + day + view count |

On first start with an empty database, `seed.js` loads the publication and article archive (and the default admin user).

**Database connection order** (`server/src/db.js`):

1. Use `MONGO_URI` if set  
2. Else try local `mongodb://127.0.0.1:27017/zamanadil`  
3. Else start an in-memory MongoDB for development

## Archive desk (admin)

Path: `/admin` (sign-in at `/admin/login`).

### Auth

1. Login posts username/password to `POST /api/admin/login`.
2. Server checks bcrypt hash and sets an **httpOnly** cookie (`za_session`) with a JWT (12-hour expiry).
3. First login requires a **password change** (`mustChangePassword`) before desk routes work.
4. Desk routes use `requireDesk` (valid session + password already changed).
5. Logout clears the cookie.

Default credentials for local setup are documented in `README.md`.

### What the desk can do

- Dashboard stats: counts, unread messages, top pages, publications missing links
- Create / edit / delete **publications** (including DOI, URL, PDF links)
- Create / edit / delete **articles** (reviews and opinions)
- Read, mark-read, and delete **contact messages**
- Change admin password

Admin API is under `/api/admin/*` and is not available to anonymous visitors.

## Request lifecycle (summary)

**Visitor opens Publications**

1. React route `/publications` mounts  
2. `GET /api/publications`  
3. Mongo returns sorted records  
4. UI lists them; each title can open journal / DOI / PDF as stored in the desk  

**Visitor sends Contact**

1. Form → `POST /api/contact`  
2. Validation + rate limit  
3. `Message` document created  
4. Appears in admin Messages  

**Owner updates a publication**

1. Signs in → JWT cookie  
2. Desk form → `PUT /api/admin/publications/:id`  
3. Mongo updated  
4. Public list/detail immediately reflect the change

## Running the system

```bash
npm install

npm install --prefix client
npm run dev
```

Optional: copy `server/.env.example` to `server/.env` and set `MONGO_URI`, `JWT_SECRET`, `CLIENT_ORIGIN`, and `PORT` for a real database and production-safe sessions.
